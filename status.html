Development Status

What’s built, what’s partial, what’s open

Raphael runs end to end: Google sign-in, streaming brain-agnostic chat, a real memory layer, working tools, and four feature surfaces (tasks, reminders, fitness, nutrition) each with both doors — a REST route the UI hits for free, and a chat tool that reaches the same route. This page is the honest snapshot. The durable design lives in architecture.html.

5 services · 18 migrations 278 unit tests + a 10-stage e2e 3 provider paths latest: observability + one-command dev loop
Google Sign-In is the only way in. The passwordless dev-login endpoint has been deleted from the code — handler, route and config flag — so no env var can re-open it. An uninvited email is rejected at the callback; the very first sign-in ever bootstraps the admin.

Working today

Exercised end to end, by the e2e script or by hand through the UI.

Google sign-in, invite-only

First Google sign-in bootstraps the admin (race-safe under an advisory lock); everyone after needs an allowed_emails invite, which is consumed on use. Uninvited → 403, nothing stored.

Durable sessions, short-lived tokens

Opaque session id in Redis behind an httpOnly cookie (7d, revocable); /auth/session trades it for a 1h access JWT held in memory only. Logout is a real revoke.

Brain-agnostic streaming chat

SSE token stream from whichever provider the admin activated system-wide. Capabilities (window, native tools) are probed per request, never cached at boot.

The lifeboat

A rejected credential (401/403/402) degrades visibly to the local row with a banner, and the answering model is stored on the message. A 429 or 5xx errors instead — no silent swap, and is_active is never touched.

Memory that earns its keep

Durable fact triples + episodic notes, hybrid FTS + pgvector retrieval fused with RRF, a relevance floor, access-driven reinforcement, a daily reaper, and a synthesized user portrait. Embeddings are in-process — no key, no network, no failure mode.

Tools that actually fire

22 tool definitions across tasks, reminders, fitness, nutrition, calendar and web search, run in a bounded pre-flight (max 2 rounds, one write per domain per turn) — never a streaming agent loop, never an LLM call inside a handler.

Two doors, everywhere

Every feature is UI-first REST at zero tokens; chat reaches the same routes. Reminders and the fitness coach fire from plain Go schedulers with no model in the loop at runtime.

Same-origin web

Next rewrites /api and /auth to the gateway server-side, so the browser never makes a cross-origin call. One port to expose; CORS and the SameSite cookie split disappear. Data fetching is TanStack Query with a 30s stale time.

A frontend you can find things in

The 1 966-line page.tsx is split: ~395 lines of auth shell, all chat in app/chat/ChatView.tsx, settings in app/settings/, and login / onboarding / notifications as their own files. Chat stays mounted on every tab and is hidden with CSS, so a tab switch no longer aborts a streaming reply.

Logs you can actually read

All four services emit one JSON schema, a request id crosses every hop, and ./dev.sh / ./logs.sh / ./stop.sh make the whole stack one command. Loki + Grafana behind an opt-in compose profile when grep isn't enough.

Label hygiene, so Loki stays fast

  • Labels (indexed): service, level, job — bounded, ~6 × 4.
  • Structured metadata (queryable, no new streams): request_id, user_id — as labels they would create one stream per request and melt the index.
  • Line body, parsed at query time: method, path, status, duration_ms, err.

The query that matters

{job="raphael"} | json | request_id="<id>" — one chat turn, every service that touched it, in time order.

Everything wrong, everywhere

{job="raphael", level="error"}. Or without Grafana at all: ./logs.sh | grep -E 'ERROR|"level":"error"'.

Slow paths

{job="raphael"} | json | duration_ms > 1000, and sum by (service) (rate({job="raphael", level="error"}[5m])) for a rate graph.

Partial — real, but with a stated ceiling

These work. They just don’t work as widely as a reader might assume.

  • Provider parity is designed for, not proven for partial All three adapters exist and capabilities are probed at runtime, but the e2e script drives a local Ollama model. The OpenRouter path and the Claude api_key path are exercised by unit tests and by hand, not by an automated cross-provider run.
  • The Claude OAuth path is degraded by design by design anthropic_cli goes through the claude-agent-sdk CLI door and yields no native tool_use blocks, so native_tools=false. On that path only web_search keeps its keyword fallback; tasks, reminders, fitness, nutrition and calendar are simply not offered. Refusing is the intended behaviour — but it means "tools work" is only true on two of the three paths.
  • Tool selection is a keyword gate deliberate Which tool sets get offered is decided by substring matching, with no model involved — that is the token-minimization win. The cost is recall: an unusually-phrased request may never reach its tool. The UI door is the fallback. Upgrade path is a cheap classifier on the free credential.
  • Scale-out is single-instance-shaped partial Both schedulers claim rows FOR UPDATE SKIP LOCKED, so a second instance is safe. But the agent-svc reaper is a naive fixed-interval daemon thread rather than pg_cron, the Ollama capability probe is cached for the process lifetime (a pulled model or a changed num_ctx needs a restart), and the Google-login bootstrap uses a single global advisory lock.
  • Frontend test coverage is thin partial Two node test files (gateway.test.ts, quests.test.ts). The ~6 800 lines under web/app/ are covered by in-file dev-only self-checks and by using the app, not by a suite. The page.tsx split made the code findable; it did not make it tested.
  • Observability is logs, not telemetry partial Structured JSON everywhere, a request id across every hop, /health on all four, a config banner, and Loki/Grafana on an opt-in profile. What is still absent: no metrics endpoint, no OpenTelemetry, no distributed tracing. A request id correlates log lines; it is not a span tree, and there is no latency histogram or error-budget signal anywhere.
  • Request-ID propagation stops at agent-svc's outbound calls known gap agent-svc's own httpx calls to user-svc and conv-svc do not forward X-Request-Id, so the callees mint a fresh one. A trace is complete from the browser down to agent-svc; the writes agent-svc then makes appear under ids of their own. The fix is one shared header injector on the httpx clients.
  • Central logging is dev-shaped by design Alloy tails host files in ./logs because in dev the five services are host processes, not containers. A containerized deployment would need a docker/journald source instead. Retention is 7 days, and Grafana's default credentials are admin/raphael unless GRAFANA_USER/GRAFANA_PASSWORD are set before its first start.

Known open items

Things that exist and are wrong, risky, or drifting. None are hidden.

  • Migrations do not auto-apply to an existing database operational ./db is mounted at /docker-entrypoint-initdb.d, which Postgres runs only on a fresh volume. A newly added file does nothing until someone runs it with psql. Symptom: a feature 500s with "relation does not exist". fitness_coach.go already carries a guard comment about exactly this for db/018. There is no migration runner and no applied-versions table.
  • Login over the devtunnel is not yet human-verified unproven The same-origin proxy, GATEWAY_INTERNAL_URL, ALLOWED_DEV_ORIGINS and the env -u NEXT_PUBLIC_GATEWAY_URL guard in dev.sh all exist so that a Google sign-in works through a tunnel. Nobody has actually completed that round trip from a remote device yet. Until someone does, treat remote login as unproven, not working. The AuthProvider/React-context refactor is deliberately parked behind this — token and onFail are still threaded as props to every tab, and changing how auth state propagates while the auth path itself is unverified would make a failure impossible to attribute.
  • .env.example has drifted from the code docs It still sets NEXT_PUBLIC_GATEWAY_URL to an absolute URL (the current intent is empty, i.e. use the same-origin proxy) and does not mention GATEWAY_INTERNAL_URL, ALLOWED_DEV_ORIGINS, CORS_ORIGINS/WEB_ORIGIN, ACCESS_TTL/SESSION_TTL, RATE_LIMIT_PER_MIN, SYSTEM_CONFIG_UID or GRAFANA_USER/GRAFANA_PASSWORD at all. LOG_LEVEL did get added. Worse than an omission: the root .env carries a comment explaining that NEXT_PUBLIC_GATEWAY_URL must not be set there, and .env.example — the file people copy — sets it.
  • No CI, so portability rule 6 is unmet gap There is no .github/ workflow. "The suite runs against Ollama on every commit" is an intention, not a fact — make test and scripts/e2e.sh are run by hand. The fallback you never test is not a fallback.
  • Redis loss is a full logout accepted Sessions live only in Redis, which runs with --save "" --appendonly no. A restart or eviction signs everyone out. Fine for dev; a decision to make explicitly before any real deployment.
  • Provider config is system-wide, not per-user by design The resolver reads credentials under SYSTEM_CONFIG_UID for every caller, so one admin choice is the brain for everyone. This is intentional today, but the provider_credentials table is still per-user shaped and older notes describe a per-user picker — a real source of confusion when reading the code.
  • agent-svc is a heavy image accepted CPU torch plus the encoder weights baked in at build. Baking them is the right call (zero cold-start fetch, works offline), but the image is by far the largest artifact and is the obvious optimization target.
  • Calibration knobs that are guesses, not measurements tune Marked in-source: the retrieval relevance floor and reap threshold ("starting guess, NOT derived — tune against ~200 real turns"), the ~4-chars-per-token estimate in the budgeter, and OLLAMA_NUM_CTX, which must be set to match your Ollama's real num_ctx — over-claiming truncates in silence.

Not built

Described somewhere in the plan, no code today. Listed so the status can’t be read as more finished than it is.

Integrations

  • Gmail — no code. Scopes were deliberately kept off the restricted list.
  • Google Drive — no code.
  • GitHub — no code.
  • Calendar is read-only; there is no create/modify event path.

Platform

  • No separate worker service and no Redis Streams. Recurring work is done by two in-process Go schedulers in user-svc plus one daemon thread in agent-svc — a deliberate divergence from the original plan, and simpler, but it is not the described architecture.
  • No cloud infrastructure. No Terraform, no ECS task definitions. docker-compose.yml is the only deployment artifact.
  • No CI/CD.
  • No planner/executor split or subagents. The pipeline is a straight line with a bounded pre-flight, on purpose.

Product

  • Mobile app, voice, multi-agent marketplace, user-authored agents — all still ideas.
  • Delivery channels beyond the in-app feed (push, WhatsApp outbound) — the sink is decoupled and ready for an adapter, but none is written.

What the e2e proves that unit tests can’t

  • The lifeboat fires on a real 401 from a real provider, exactly once, and a 429 does not fire it.
  • No provider wire format (toolu_, call_, thinking blocks, cache_control) ever reaches Postgres — scanned directly in the database, including messages.tool_calls, which is now genuinely populated.
  • The two doors converge: a REST-created task and a chat-created task land as the same row shape, and the REST path writes no message and spends no tokens.
  • The skip-gate holds: a contentless turn stores no fact.

Immediate next steps

Ordered by "what would hurt most if it stayed as it is".

  1. A migration runner. An applied-versions table and a make migrate that runs pending db/*.sql in order. Every file is already additive and idempotent, so this is bookkeeping, not surgery — and it removes the single most likely way to break a running install.
  2. Verify a real Google login through the devtunnel, by hand, from another device. It is the last unproven link in the same-origin-proxy work, it is fifteen minutes, and the AuthProvider refactor is queued directly behind it. Turn both dev-auth switches off first.
  3. CI, running the suite against Ollama. Closes portability rule 6, and turns "green when someone last ran it" into a fact. Should also run the e2e against the local model.
  4. Reconcile .env.example with the code and note the exposed-deployment checklist (both dev-auth switches off, GATEWAY_INTERNAL_URL + ALLOWED_DEV_ORIGINS set, NEXT_PUBLIC_GATEWAY_URL empty) next to it.
  5. Prove the OpenRouter and Claude paths the way the local path is proven — one e2e run per provider tier, so parity stops being an assertion.
  6. Close the request-ID gap in agent-svc — one header injector on its httpx clients — so a single trace covers the writes it makes downstream, not just the turn itself.
  7. Tune the guessed knobs against real data: the retrieval relevance floor and the reap window, once there are ~200 real turns to measure against.
  8. Decide on session durability before any deployment: either accept "a Redis restart logs everyone out" in writing, or turn on persistence.
  9. Then, if the integrations still matter: Gmail is the largest remaining gap, and it is a scope/verification decision before it is a code decision.
