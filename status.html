What’s built, tested, and running

A brain-agnostic, memory-backed chat assistant runs end to end today — five services, provider fallback, in-process embeddings, and a full container stack. This page is the honest snapshot: what works, what’s partial, and what has no code yet. Read it next to architecture.html and plan.md.

Some seams that do exist are hollow or broken — those are listed under Known issues, not hidden.

What works today

The end-to-end path a user actually exercises.

Brain-agnostic chat

Dev-login → message → the gateway streams tokens over SSE from whichever provider the user activated (seeded default: local Ollama qwen2.5:7b).

Memory that outlives providers

Each turn is embedded in-process (nomic, 768-d) and stored in pgvector; retrieval is cosine top-k, budgeted to the active model’s context window.

The lifeboat

If the active credential is rejected (401/403/402) the designated fallback answers with a visible “degraded” banner. Rate limits and outages error instead — no silent swap.

Settings & safety

A Settings tab manages providers and picks the fallback. Keys are AES-256-GCM encrypted; the internal key-serving route is shared-secret gated.

Not built yet

Described in the plan, no code today. Being explicit so the status isn’t read as more finished than it is.

  • Tools & integrationsNo tools/ directory. Gmail, Calendar, Drive, Web Search, GitHub — zero implementation. The neutral tool-call plumbing exists; the pipeline never passes tools.
  • Background workersNo worker service, no Redis Streams consumer. Email monitoring / scheduled tasks / daily summaries absent.
  • Real OAuth loginOnly POST /auth/dev-login gated by DEV_AUTH_ENABLED. No identity provider, no Google OAuth connections.
  • Planner / executor / tool loopThe pipeline is a fixed 4-step line; no capability-based branching or subagents.
  • Monitoring & CI/CDNo OpenTelemetry/metrics beyond /healthz & /readyz; no .github/ workflow, so “CI runs the suite against Ollama” is not yet true.
  • Cloud infrastructureNo Terraform, no ECS task defs. The full compose is the only deployment artifact; AWS is described, not provisioned.

In design

Being designed right now. None of this is written — no code, no schema, no branch. Listed so the direction is legible, not so it reads as progress.

  • Proposed Memory-layer overhaulTyped facts with confidence/importance; a knowledge graph as a triples table; LLM extraction from ordinary chat; decay, reinforcement, consolidation; hybrid FTS+vector retrieval fused with RRF. Aimed at the memory gaps listed under Known issues.
  • Proposed Vendor-neutral tool-calling loopWould activate the plumbing that already exists but is dead today. Estimated ~1.5 days.
  • Proposed Fitness featurefitness_events (JSONB) + fitness_goals, roughly 3 tools, coach-context computed on read. Estimated ~4 days total, including the tool loop it depends on.
  • Proposed Standing constraint: every feature works on all three provider pathsA requirement from the user, not a claim about code. local (Ollama), openai_compat (OpenRouter), anthropic (Claude). Not identical behavior — each feature declares a capability tier and a stated fallback, and degrades visibly rather than silently. The durable version lives in architecture.html.

Known issues

Different from “not built”: these seams exist and are broken, hollow, or lying. Verified against source at 423f8be. All unfixed.

  • No short-term memoryOnly the current message reaches the model — graph/workflow.py:117 builds messages = [{"role": "user", "content": state["message"]}] and nothing else. History is persisted to conv-svc (workflow.py:128-142) but is never read back into the prompt. “What did I just say?” fails.
  • The tool-calling layer is ~60% built and completely deadEvery signature takes tools=None (llm/base.py:39,41) and every adapter ignores it (anthropic_api.py:72,85 · anthropic_cli.py:116,135 · openai_compat.py:47,62). ChatResponse.tool_calls exists (base.py:30) and every chat() hardcodes tool_calls=[] (anthropic_api.py:80 · anthropic_cli.py:145 · openai_compat.py:58). The real translator neutral_from_anthropic() (anthropic_api.py:18-37) does strip toolu_ ids correctly, but no tools are ever sent, so no tool_use ever comes back. conv-svc/toolcalls.go is a complete 52-line validator with a passing test — guarding a column that has never been written.
  • e2e stage 5 is half a vacuous testscripts/e2e.sh:94-97. The first clause — scanning content for toolu_/call_/"thinking"/cache_control — is meaningful and does real work. The second clause scans messages.tool_calls (db/001_init.sql:33), a column that is always NULL because persist_node posts only {role, content} (workflow.py:121-125). That half has never had a chance to fail.
  • Memory stores raw transcript turns, not factsmemory/retriever.py:55 remember() embeds the user message and the answer verbatim (called from workflow.py:149). No extraction, no dedup, no decay, no importance, no expiry — the table grows unbounded.
  • Missing nomic task prefixesThe encoder is nomic-embed-text-v1.5 (llm/embeddings.py:3), trained with search_document: / search_query: prefixes. Neither string appears anywhere in embeddings.py or retriever.py. Omitting both measurably degrades retrieval.
  • No relevance threshold on retrievalretriever.py:23 retrieve(..., k: int = 5) runs ORDER BY embedding <=> %s::vector LIMIT %s with no distance cutoff, so it always fills top-5 — a barely-related row still gets injected under a “Relevant memories about the user” framing. Only a token budget trims it (retriever.py:44-52).
  • Fresh clone fatals on a missing internal tokenINTERNAL_TOKEN= is empty in .env.example:35 and never auto-generated — user-svc fatals on first boot.
  • Dormant: gateway injects a field conv-svc rejectsgateway/proxy.go:88-96 injects user_id into any JSON write body, including POST /conversations/:id/messages, but conv-svc/handlers.go:252 sets dec.DisallowUnknownFields() — that route would 400. Dormant only because nothing exercises it.
  • Dead config varsNever read: WEB_PORT (.env.example:13), OLLAMA_MODEL (:44), SEED_ANTHROPIC_API_KEY / SEED_OPENROUTER_API_KEY (:52-53).
  • A migration comment that liesdb/002_lifeboat.sql:18 reads “STATUS: staged, NOT YET APPLIED”. False: docker-compose.yml:19 mounts ./db:/docker-entrypoint-initdb.d:ro, so all of db/ including 002 is applied automatically on a fresh Postgres init. Still true at 423f8be; corrected to “STATUS: applied” in the working tree, uncommitted.
  • make test breaks off WindowsMakefile:38 hardcodes .venv/Scripts/python.exe. Still true at 423f8be; a fallback fix exists in the working tree, uncommitted.
