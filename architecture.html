Raphael

A brain-agnostic, memory-backed personal assistant. Five services, one Postgres, one Redis. Every feature has two doors: a REST route the UI hits directly at zero LLM cost, and a chat tool that reaches the same route when you'd rather just say it. The model behind it is swappable — local Ollama, OpenRouter, or Claude — and nothing in the database knows which one answered.

01What Raphael is, and the three principles

Read this section first. Almost every design decision in the rest of the document is one of these three principles applied to a new surface.

Principle 1 — Two doors, and token minimization

Every feature is a set of user_id-scoped REST routes. The UI calls those routes directly and spends zero LLM tokens. Chat reaches the same routes through a tool, so tokens are spent only on the natural-language part — compiling "remind me to call mum every Tuesday at 6" into {kind:"cron", cron:"0 18 * * 2"} exactly once, at authoring time. After that the reminder fires from a plain Go scheduler forever, with no model involved.

Corollaries you will meet repeatedly: tools are gated by a cheap keyword check before any model sees them; scheduled/background work is templated text, never generation; a tool handler is one httpx call and never an LLM call.

Principle 2 — Provider portability

A feature is not done until it works on all three provider paths: local (Ollama), openai_compat (OpenRouter) and anthropic (Claude). Not identical behaviour — each feature declares the capability tier it needs and the fallback it takes when a path can't meet it, and it degrades visibly, never silently. "Claude-only" is not a shipping state. Nothing provider-specific is ever persisted.

Principle 3 — Per-user context isolation

Members are fully isolated. Every query is WHERE user_id = $1, the user_id is forced from the verified JWT at the gateway and never read from a client body, and a chat turn's context is always single-user. The only cross-user reads in the system sit behind requireAdmin, which re-reads users.role from Postgres on every hit.

Migrations are additive, idempotent, and applied by hand after the first boot

docker-compose.yml mounts ./db at /docker-entrypoint-initdb.d, which Postgres runs only on a fresh data volume. On an existing database, a new migration file does nothing until someone applies it with psql. Code must therefore tolerate its table not existing yet — fitness_coach.go logs and continues rather than crashing when 018 hasn't been applied. Every file uses IF NOT EXISTS / ADD COLUMN IF NOT EXISTS and never DROPs or deletes rows, so re-running the whole directory is safe.

04Auth & RBAC

Google Sign-In is the login. Invite-only after the first admin. Two tokens, on purpose.

Sign-in

One consent grants identity and calendar read access, so the Google credential row is written on login. An uninvited email is rejected before anything is stored.

The two-token session model

Durable: an opaque session cookie

  • 32 random bytes, base64url — not a JWT. It carries no claims.
  • Redis session:<id> → {uid, role}, TTL SESSION_TTL (default 7 days).
  • httpOnly cookie, name from SESSION_COOKIE_NAME (default raphael_session).
  • Server-side revocable: POST /auth/logout is a real DEL.
  • lookupSession fails closed — a missing key, a bad value, or a Redis error all mean "cannot prove this session", i.e. 401.

Working: a short-lived access JWT

  • HS256, claims sub + role, expiry ACCESS_TTL (default 1h).
  • GET /auth/session trades the cookie for a fresh one and returns the user.
  • The SPA holds it in memory only — never localStorage. A hard refresh re-calls /auth/session.
  • The refresh is single-flighted client-side so a dashboard mount doesn't fire N parallel refreshes and trip the rate limiter.
  • A short expiry bounds the damage of a leaked token.

/auth/session also stamps users.last_active, throttled to at most one write per uid per 5 minutes via SET NX EX active:<uid> — otherwise every page refresh would be a database write.

Roles

  • The JWT role claim is a UI hint only. It decides whether the Admin tab renders. It grants nothing.
  • requireAdmin re-reads users.role from Postgres on every privileged hit. A member with a stale or crafted claim cannot escalate — fail closed.
  • Admin powers: list users (active + pending invites, with last-active), change a role, remove a user, manage allowed_emails, and edit the system-wide provider/model config. All of it is pure REST, so administration costs zero LLM tokens.
  • Members see none of it, and no member-facing route can read another user's rows.

Hazard — the dev-login backdoor

POST /auth/dev-login takes an email, no password, upserts a user, and mints a valid JWT. It is mounted only when DEV_AUTH_ENABLED=true (the config default is false, deliberately fail-closed), and the web button only renders when NEXT_PUBLIC_DEV_AUTH=1. Signing in as the seeded …0001 address returns role admin.

Turn both off whenever the app is reachable beyond localhost — a tunnel, a LAN IP, a deployed host. Left on, it is an unauthenticated admin door. Tests must also never use the DEV_UID account: it is the human's real data. Use a dedicated dev-login test user.

05The chat pipeline & the tool pattern

agent-svc/src/graph/workflow.py. Four steps in a fixed order, no branches, no cycles, no graph engine — run() is a straight sequence of calls, and extraction deliberately sits outside it.

The four steps

StepDoesFailure behaviour
context_node Reads the active model's window, computes three budgets, then fetches history, retrieval and portrait concurrently (all three are I/O- or torch-bound and release the GIL, so latency is the slowest, not the sum). Each source degrades independently to empty. An empty context must never break a turn.
generate_node Pre-flight tool decision, then exactly one streamed answer wrapped in the lifeboat. A pre-flight exception is swallowed — a search or tool problem may never break the turn.
persist_node POSTs the user turn and the assistant turn to conv-svc with provenance. Returns the real row id or None. It never fabricates a uuid for persisted_message_id, because that value is an FK target.
done_node Emits the terminal done event and logs one line per turn. Token counts are omitted when unknown — never reported as a false 0.

Lucky ordering, stated because it breaks silently: generate runs before persist, so at generate time the current message is not yet in conv-svc. history is exactly the prior turns and the pipeline appends the current one itself. Move persist_node above generate_node and every turn double-counts.

The two-door tool pattern

Tools do not run in a streaming agent loop. They run in a pre-flight: one or two non-streaming chat() calls before the answer stream begins. Three reasons, all load-bearing:

  1. stream() is never touched. chat() already owns the unsupported-parameter probing ladder and the 400-retry, so a deployment that rejects tools demotes to the fallback tier for free.
  2. stream_with_lifeboat runs exactly once per turn by construction, not by a guard someone can delete. That is what makes "at most one degraded event per turn" true.
  3. No LLM call is ever nested inside a tool handler. Each handler is a single httpx request. main.py drains a queue.Queue from a daemon thread — a nested model call deadlocks it.

Gating, tiers and loop discipline

  • Keyword gate first. looks_task_related(), looks_reminder_related(), looks_fitness_related(), looks_nutrition_related() are cheap string checks with no model involved. If nothing matches and search/calendar are off, _preflight returns immediately — a non-tool turn never pays for the tool-decision call at all. This is the token-minimization gate.
  • Tier 1 — native_tools = true: the real neutral tool definitions are offered, capped at _MAX_PREFLIGHT_ROUNDS = 2 (a module constant, not config: an operator who can set it to 20 has an agent loop).
  • Tier 2 — native_tools = false: only web_search has a keyword fallback (a hint-word check turns the raw message into the query). Calendar, tasks, reminders, fitness and nutrition are simply not offered — no keyword can guess a task_id, a calendar window, or compile a schedule into cron. Refusing is the honest fallback.
  • A write is terminal. Each domain may fire at most one mutating tool per turn, and any write ends the loop, so a confused model cannot double-submit a reminder or log a workout twice.
  • A read may earn a second round. list_tasks/list_reminders hand their result back as plain role/content turns (every adapter reads those; no provider-specific tool-result shape has to be invented) so a follow-up round can resolve "mark my milk task done" to a real id.
  • _TOOL_DIRECTIVE is appended to the system prompt for the decision call only. The persona is warm and biased toward short replies, which makes a small local model say "Got it, I'll remind you!" and call nothing. The directive says: a reminder only exists once you call its tool. It is dropped for the streamed answer so the reply keeps the persona's voice.
  • reasoning=False on the decision call. A thinking model leaves content and tool_calls empty while it deliberates and burns the whole 512-token budget, so tools never fire. Thinking stays on for the answer stream.
  • Everything is non-fatal and honest. A failed tool contributes a block that tells the model it failed, so the turn lands ungrounded but never lies.

Tool definitions are neutral {name, description, parameters}. Each adapter converts on the way out (Claude wants input_schema, OpenAI-compatible wants parameters). The persona and the prompt

build_system() assembles the system prompt in a deliberately cache-friendly order — stable first, volatile last: persona base → portrait → fact profile → retrieved notes → search block. A prefix cache only pays if the part that changes every turn is at the end.

  • The persona is a warm, capable "evolved sage": lead with the answer, default to 1–4 sentences, go long only when asked, and say plainly when unsure.
  • build_system([], []) is byte-identical to SYSTEM_BASE. A test asserts it, and both derive from _persona(), so the two can never drift.
  • The assistant's name is set in the prompt and declared authoritative there, because a stale memory can claim a previous name.
  • Trust boundary: the name and the portrait land verbatim in the prompt, so both are stripped of non-printable characters and hard-capped (40 and 600 chars) at injection time — again, even though the portrait was already sanitized at write time.

06Model layer & provider portability

agent-svc/src/llm/ — one resolver, three chat adapters, one local encoder.

Provider config is admin-owned and system-wide

The resolver fetches credentials under SYSTEM_CONFIG_UID for every caller, not under the requesting user's id — one active model for the whole deployment, edited by an admin through /api/admin/providers. The table, the one-active index, the lifeboat and the portability semantics are all unchanged; only the owning row differs. Per-user Google tokens remain keyed to each member's own uid.

Selection has no precedence and no chain: someone picks, the resolver reads that row. resolver.extractor() is the exception — background work (fact extraction, portrait synthesis) is only allowed to run on the free local/lifeboat credential, never on a paid key, because silently doubling someone's spend on work they didn't ask for is not acceptable.

Claude has no embeddings endpoint and no token changes that. We don't solve it with a second provider; we solve it by not needing one. The encoder ships in the image, which is also what makes vectors outlive any credential — if embeddings came from a paid API, an unpaid bill would strand every vector in memories: you'd keep the rows but could no longer produce a query vector in the same space. Losing Claude must cost reasoning quality, never memory.

The lifeboat: an error path, not a preference ordering

transient 429 · 5xx · timeout · connection

The credential is fine, the provider is not. The request errors — an error event, and the turn stops. We do not answer with a different model at a different cost and quality and say nothing about it.

dead credential 401 · 403 permission · 403 billing · 402

The credential is dead. The lifeboat fires: a degraded event goes out first, the answer re-streams on the designated local row, and degraded=true + the answering model/provider are stored on the message. No lifeboat configured ⇒ error.

  • The lifeboat never flips is_active. There is deliberately no such call in the module. Your configuration stays yours; we answer once, visibly degraded.
  • It never fires silently — the banner is the point. Your Claude key expiring should make the assistant visibly dumber, not take it down.
  • On a degraded turn, state["provider"] still points at the credential that just 401'd. Post-stream extraction must use resolver.extractor(), not that handle. (This trap is documented in the code; it would fail on every degraded turn.)

The portability rules

  1. Every feature ships on all three provider paths. Declare the capability tier it needs and the fallback it takes; degrade visibly.
  2. Never persist a provider's wire format. It lives inside the adapter and dies there.
  3. The encoder ships with the app. See above — this is the memory guarantee.
  4. Messages are neutral. tool_calls is our {name, arguments} shape, not Anthropic's tool_use block and not OpenAI's array.
  5. Ask the provider what it can do. capabilities() is read per request, never cached at boot: a retrieval budget sized for a 1M window overflows an 8k local window on the exact turn you fall back to it.
  6. The fallback you never test is not a fallback. gap There is no CI workflow in the repo today, so "the suite runs against Ollama on every commit" is an intention, not a fact. Run make test and scripts/e2e.sh by hand.

Why we own the loop

A harness is the agent loop: call the model, run the tool it asked for, feed the result back, repeat. Anthropic ships three — Tool Runner, Managed Agents, and the Claude Agent SDK — and all three are Claude-only; none accept an Ollama or OpenRouter endpoint. Any harness would also want to own the loop, and two harnesses cannot both own it.

Decision: our loop owns the loop; Claude is just a provider. LangGraph was tried and dropped too — the pipeline is a straight line, so a graph engine earned nothing. Cost: no hosted sandbox, no built-in tools, no session resume — we build those. Buys: one loop, one set of tool definitions, one set of bugs, and identical behaviour whether or not a Claude token exists. Revisit only if the local-model path is ever dropped.

Per-user tokens are always passed explicitly (anthropic.Anthropic(api_key=…)). Never let an SDK fall back to the process environment in a multi-user service: an unset ANTHROPIC_API_KEY doesn't mean "no credentials" — the SDK also reads ANTHROPIC_AUTH_TOKEN and an on-disk auth profile, so one user's request can silently bill the host's key.

retriever.pyLong-term retrieval and writing. One connection, three queries per turn; also owns write_facts, write_notes, touch and reap.
rank.pyThe pure, testable half: Reciprocal Rank Fusion (RRF_K = 60) and re-ranking. No DB, no I/O.
budget.pySplits the active model's window into (profile, memories, history) token budgets. Fractional, not a flat cap — a flat cap is why a 1M window and a 32k window once got the identical 4000 tokens, so paying for a bigger model bought nothing. Ceiling 24k, floor 384.
extract.pyLLM extraction of durable facts from an ordinary turn.
portrait.pySynthesizes the persona card from the fact list.
read.pyRead-only projections for the dashboard and knowledge graph. Never selects the embedding column; degrades to an empty-but-valid shape, never a 500.

Retrieval

  • Hybrid, fused by rank not score. A Postgres FTS pass and a pgvector cosine pass, each pulling k*2, fused with RRF — because ts_rank and cosine distance are not on the same scale and never will be, so we fuse the order, not the numbers. A row found by both passes beats a row found by one; that is the entire point of running two.
  • Plus a query-independent profile pass over facts (confidence >= 0.5, top 8 by importance). This is the only reader of facts.
  • Both passes read live rows only (valid_until IS NULL). The vector pass additionally pins embedding_model.
  • Encoder dead ⇒ FTS-only. Recall drops; memory lives.
  • Never raises. Any exception returns the empty shape.
  • Query text is embedded with the search_query: nomic task prefix; stored text uses the document prefix.

Writing, reinforcement and decay

  • Facts are triples. Re-hearing one is an upsert that bumps times_seen, not a second row — the DB's generated normalized columns make that dedup unbypassable.
  • Notes are episodic rows. There is deliberately no remember() for raw turns: the transcript already lives in conv-svc, and copying it into memories was the original unbounded-growth bug.
  • Reinforcement: touch(injected_ids) bumps access_count/last_accessed on whatever was actually injected — run after the stream, off the critical path, because retrieval is what the user waits on and must not pay for a write.
  • Decay: a daily reaper thread archives episodic rows with times_seen <= 1 that are stale and unaccessed, by setting valid_until — one statement drops them from both retrieval and the partial index. Facts are never archived; they are superseded by upsert. A failed reap is a no-op.
  • Extraction runs after every exchange, on resolver.extractor() only. A skip-gate short-circuits it when the user's message has no content words (an "ok" or "2+2" turn is a provable no-op) before spending anything. The JSON ladder is cheapest-first: json_mode + reasoning=False where supported (the provider remembers a 400 downgrade per model) → a prompt a 7B model survives (flat items, one worked example, an explicit empty literal, a hard item cap) → json.JSONDecoder().raw_decode, which stops at the first valid value so fences and preambles fall out for free. Every item must be grounded against a content word of the user's message.
  • Portrait synthesis runs on the same daily thread, on the same free credential, and skips the LLM when fact_fingerprint is unchanged. Injection is a stored-string read: zero extra per-turn tokens.

Prompt-side guardrails

Retrieval that always fills top-k will hand the model a barely-related row, and a model handed notes about a person will happily narrate that person's life back at them. Three static blocks in workflow.py fix that, and they cost zero per-turn tokens because they never change:

ConstantWhereWhat it prevents
_PRECEDENCEtop of the notes block Calls the notes what they are — "retrieved from past conversations, may be stale, wrong, or irrelevant; what the user says NOW always wins". The header is deliberately not "Relevant memories": top-k always fills, so rank 5 of 5 is "the closest thing I found", and asserting relevance is how a 0.3-confidence guess gets obeyed like a directive.
_BINDINGinside the notes block only Anti-confabulation. Use the notes silently; never recite or list them; never invent an intensity, frequency, backstory, nickname or mood beyond exactly what a note says. In particular, on a bare greeting reply with a plain greeting and nothing about the user. Living inside the notes block means it never reaches an anonymous turn.
_TOOL_DIRECTIVEdecision call onlyA friendly "I'll remind you!" that creates nothing. See §5.
name-authority linewith the notesA stale note claiming the assistant has a different name overriding the configured one.

08Feature subsystems

All three follow the same shape: uid-scoped rows in user-svc, a REST door, a tool door, and any recurring work done by a plain Go scheduler with no model in the loop.

Tasks

  • Three-column Kanban (To Do / In Progress / Done) with priority and drag-reorder, plus an RPG-flavoured quest presentation in web/lib/quests.ts.
  • Reorder writes position (a double, so an insert between two rows needs no renumbering).
  • Four chat tools; list_tasks returns lines carrying task_id so a second pre-flight round can resolve a natural-language reference to a real row.

Reminders + the notification feed

  • Authoring is the only place tokens are spent. The chat tool compiles NL into {text, kind, cron|fire_at, until, window} once. The UI form produces the same fields for free.
  • The server never trusts the model's scheduling maths. timezone is force-stamped from users.timezone, and next_fire is computed server-side by cron.go. The tool sends local ISO-8601 without an offset; user-svc interprets it in the user's zone.
  • cron.go is a small 5-field cron parser plus computeNext(), which advances from the fire time rather than from "now", so a slow tick cannot make a schedule drift.
  • The scheduler is LLM-free. It polls WHERE active AND next_fire <= now(), claims each row FOR UPDATE SKIP LOCKED, writes a notifications row, and advances next_fire — all in one transaction, so a crashed worker auto-recovers and a second instance never double-sends. A once reminder, or a cron past its until, sets next_fire = NULL, active = false and drops out of the partial index.
  • The in-app feed + unread bell is the delivery sink; other channels can be added as adapters without touching firing.

Fitness, nutrition and the coach

Shipped in two passes: db/017_fitness.sql (workouts + body metrics) and db/018_fitness_v2.sql (goals, nutrition, coach config, richer workout fields).

CapabilityHow it works
Logging Workouts, body metrics and meals, each through both doors. Optional fields stay NULL; date columns default to today and are read back with to_char as YYYY-MM-DD so they marshal as dates, not RFC3339 stamps.
Goal recompute Every successful workout / metric / meal write calls recomputeGoals best-effort — a recompute error must never fail the log. Progress is direction-aware: gte, lte or eq against target_value, measured from starting_value where set. Passing the test flips status to achieved, and that is never auto-reverted.
Deep stats fitnessStats: workouts this week, lifetime total, average duration over workouts that recorded one, latest weight, 30-day weight trend (latest minus the most recent reading older than 30 days, NULL when there isn't one), a 12-ISO-week zero-filled series via generate_series, lifetime count per category, and a current streak. Streaks are computed in Go from distinct workout days parsed as YYYY-MM-DD, so DST cannot shift a day.
BMI Computed on demand from the latest weight and height rows in body_metrics, converting lb→kg and in→cm first, then banded WHO-style (<18.5 underweight, <25 normal, <30 overweight, else obese). Either measurement missing returns {bmi: null, reason: "missing_measurements"} — a 200, not an error.
Nutrition Per-meal macros, per-calendar-day roll-ups, today vs. 14-day stats, and macro targets stored in fitness_config.daily_macro_targets.
Coach scheduler
user-svc/fitness_coach.go		 Templated, no LLM anywhere. A 60-second tick walks enabled fitness_config rows and can fire three things into the same notifications feed (reminder_id stays NULL): a daily check-in after checkin_time, a Sunday-evening weekly summary, and per-goal nudges. Idempotency is by stamp, not by history scan — last_checkin_at, last_weekly_at, fitness_goals.last_nudge_at — so a re-tick 60s later re-reads the stamp and skips. UI web/app/Fitness.tsx — six tabs: Overview, Workouts, Metrics, Nutrition, Goals, Trends.

Google Calendar

  • Read-only scope only (calendar.readonly), chosen so the app stays outside restricted-scope verification. No Gmail, no broad Drive.
  • The refresh token is encrypted and never leaves user-svc; agent-svc asks /internal/users/{uid}/google/token for a short-lived access token and gets None on any problem — a token lookup failure degrades the calendar tool, never the turn.
  • The tool is offered only when this user has connected Google and the provider supports native tools. There is no keyword fallback for a calendar window.

09Frontend architecture

Next.js App Router, one client shell, TanStack Query for data, and a same-origin proxy that removes CORS entirely.

Layout and view model

web/
  next.config.mjs      rewrites /api/* and /auth/* → GATEWAY_INTERNAL_URL   (the proxy)
  app/
    layout.tsx         fonts + <Providers> (QueryClientProvider)
    providers.tsx      QueryClient: staleTime 30s, retry 1, refetchOnWindowFocus false
    page.tsx           the client shell: token, user, view, conversations, SSE chat
    Sidebar.tsx        View = dashboard | chat | graph | settings | tasks | reminders
                              | fitness | admin
    Dashboard.tsx  MemoryGraph.tsx  Tasks.tsx  Reminders.tsx  Fitness.tsx  Admin.tsx
    healthz/route.ts   container liveness
  lib/
    gateway.ts         the typed API client + the SSE reader
    quests.ts          task → quest presentation
  • One shell, many views. page.tsx owns auth state and the active view; the sidebar switches a discriminated View union. The active tab is persisted to localStorage so a hard refresh returns you where you were.
  • The JWT lives in React state only — never localStorage. On mount the shell calls /auth/session to trade the httpOnly cookie for a fresh one.
  • Server components are minimal by design. Everything interactive is a client component; the App Router is used for routing, fonts and the rewrite layer rather than for RSC data fetching.

Data fetching — TanStack Query

  • Providers creates one QueryClient per browser session, lazily in state, so it survives re-renders and is never shared across SSR requests.
  • Defaults: staleTime: 30_000 (tab switches are instant from cache and revalidate in the background), retry: 1, refetchOnWindowFocus: false. Auth 401s are handled by the single-flighted session refresh, not by hammering retries.
  • Mutations invalidate the queries they affect, which is how a chat-created reminder appears in the Reminders tab without a reload.
  • Chat itself is not a query — it is a streamed fetch with a ReadableStream reader parsing the text/event-stream framing by hand (needed so the Authorization header can be sent, which EventSource cannot do).

The same-origin proxy

browser ──▶ https://<whatever-host>/api/...        (relative URL, same origin)
              └─ Next rewrite (server-side) ──▶ ${GATEWAY_INTERNAL_URL}/api/...

NEXT_PUBLIC_GATEWAY_URL = ""   ← the default; makes the client emit relative URLs
GATEWAY_INTERNAL_URL          ← where Next forwards to (default http://localhost:8080)
ALLOWED_DEV_ORIGINS           ← comma-separated extra dev hosts (tunnel domains) so
                                Next 15.5 doesn't block their HMR/_next requests

This removes cross-origin CORS, the SameSite cookie split, and the second tunnel: only the web port needs to be exposed. Set NEXT_PUBLIC_GATEWAY_URL to an absolute URL only if you deliberately want to bypass the proxy. Note that an empty value in .env reads as undefined, so the "" default is what actually applies. The gateway's own CORS config still exists for the direct-origin case and, because credentials are allowed, its AllowOrigins must stay an explicit origin list — never a wildcard.

Things that will catch you out

  • Migrations don't auto-apply to an existing volume. Newly added db/*.sql files must be run by hand with psql (see §3). Symptom: a feature 500s with "relation does not exist".
  • make dev and docker compose up collide. make up starts infrastructure only, on purpose — a bare docker compose up -d starts containerized copies of the five services on the same ports.
  • agent-svc is slow to become ready. The encoder warms at boot; /healthz reports {"deps":{"db":…,"embeddings":…}}, so wait for it rather than assuming a crash.
  • Exposing the app over a tunnel: expose only the web port, set GATEWAY_INTERNAL_URL and ALLOWED_DEV_ORIGINS, keep NEXT_PUBLIC_GATEWAY_URL empty — and turn both dev-auth switches off.
  • Never test against DEV_UID. …0001 is the human's real account with real facts and memories. Create a throwaway dev-login user instead, and never blanket-delete from facts/memories.
  • Logs are in logs/<service>.log, pids in logs/*.pid. Port stuck? lsof -i :8080.
  • Deployment artifacts: docker-compose.yml is the only one. Every service has a Dockerfile (Go services on distroless static, agent-svc on python:3.13-slim with the encoder weights baked in so there is no cold-start fetch, web on node:22-alpine standalone). There is no Terraform, no ECS task definition and no CI workflow in this repo.

11Conventions & invariants a new dev must not break

If a change makes one of these false, the change is wrong — or the invariant needs an explicit, documented decision to retire it.

#InvariantWhy it exists
1The gateway forces user_id from the verified JWT. No handler reads a uid from a request body or query the client controls.Structurally removes the entire class of "act as another user" bugs. Admin routes are the one exception, and they re-verify the role in Postgres.
2Every data query is WHERE user_id = $1. Ownership is re-checked on every operation, including updates and deletes.Per-user isolation. Cross-user reads exist only behind requireAdmin, and are read-only.
3Migrations are additive and idempotent. IF NOT EXISTS, no DROP, no down-migration, no row deletion. New file, never an edit to an applied one.The dev database holds real data and files may be applied out of order or twice.
4No LLM call inside a tool handler. A handler is one HTTP call.The SSE drain is a queue on a daemon thread; nesting a model call deadlocks it. Also the whole point of two doors.
5Exactly one stream() per turn. Never move tool work inside stream_with_lifeboat.Makes "at most one degraded event per turn" true by construction.
6Nothing provider-specific is persisted. No toolu_/call_ ids, no thinking blocks, no cache_control. tool_calls stays {name, arguments}.Provider portability, enforced by conv-svc's validator and an e2e wire-format scan.
7Capabilities are read per request. Never cache a context window or native_tools at boot.The model can change under you, and the fallback path is exactly when a stale window overflows.
8Background/unasked work runs on resolver.extractor(). Never on the user's paid credential.Silently doubling spend on work nobody asked for. Also the degraded-turn trap: the active provider handle may be the one that just 401'd.
9Memory and retrieval never raise into a turn. Degrade to empty; a DB hiccup is not a 500.Context is an enhancement, not a dependency.
10Unknown is unknown. Absent token counts are omitted, not reported as 0; persisted_message_id is the real row or None, never a fabricated uuid.A fabricated uuid violates the facts.source_message_id FK and loses the whole batch precisely when conv-svc is already down.
11Anything reaching the system prompt is sanitized at the boundary. Strip non-printables, hard-cap length — again, even if it was sanitized on write.Stored names and portraits are user-influenced text landing verbatim in a prompt.
12Auth fails closed; rate limiting fails open. A Redis error means "cannot prove this session" (401), but never a blanket lockout on the limiter.Availability where it's safe, refusal where it isn't.
13Secrets live in .env (gitignored) and never in an image or a log. api_key_enc is never returned by any API.The AES master key was once one git add away from being committed.
14Schedulers are LLM-free and idempotent. Claim rows FOR UPDATE SKIP LOCKED, stamp a clock, advance from the fire time.Two instances must never double-send, and a crash must auto-recover.
15Declare a tier and a fallback for every new feature. If a provider path can't do it, refuse visibly rather than guessing.Silent degradation is worse than a stated limitation.

Where to look when adding a feature

Migration in db/0NN_*.sql → store + handlers in user-svc/ (every query uid-scoped) → route + uid-forcing proxy in gateway/main.go → neutral tool definition + keyword gate + pure-httpx handler in agent-svc/src/tools/ → dispatcher and gate wired into _preflight in workflow.py → a view in web/app/ using TanStack Query against the REST door. That order is also the order of increasing token cost: the first four steps cost nothing at runtime.
